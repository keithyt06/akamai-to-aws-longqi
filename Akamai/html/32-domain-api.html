§4 缓存策略

API 场景下默认 NO_STORE，且 Sureroute&Caching 子规则再次强制 NO_STORE 兜底——典型的"双保险"，基本不存在意外命中。

API-DOM-4双重 NO_STORE 兜底（API 域）
双保险
双重 NO_STORE 是什么？ 第一层在 Offload origin 默认行为里把 caching.behavior = NO_STORE； 第二层在 Sureroute&Caching 子规则里再次下发 caching.behavior = NO_STORE。 两层兜底意味着即便有人改了上层的 catchall 规则，下层 Sureroute&Caching 也会把 API 默认拉回不缓存—— 这是 Akamai 针对 API 域常见的防御式配置。

Site Failover 关闭，但生产版本里开着 breakConnection 故障演练行为——迁移时必须先搞清楚触发条件，避免误伤生产流量。

API-DOM-7⚠ breakConnection: enabled=true 故障演练
高风险 · 待业务确认
⚠ 风险告警： Site Failover 已关闭，但 Property v10 的 Simulate failover 分支下 breakConnection: enabled=true —— 生产版本里开着故障演练行为。 满足特定条件时 Edge 会主动断开客户端连接。
  • 需要业务侧确认：是演练残留还是刻意保留

  • 若保留，需要在 CloudFront 层用 Lambda@Edge / CloudFront Function 主动断链（CloudFront 原生无此开关）

§10 回源请求头

Edge 向 Origin 注入的请求头——有一个几乎必然是 bug 的 header name 前导空格，迁移时需修正。

API-DOM-10⚠ XFF header " x-authentic-ip" 前导空格 bug
Bug · 迁移时必修
⚠ 强警示：几乎必然是 bug
PMUSER_CLIENT_IP 的 Parent 层 extract 指定从请求头 " x-authentic-ip"（注意前导有一个空格）提取。 HTTP 规范（RFC 7230）不允许 header name 有前导空白，任何符合规范的 HTTP stack 都不会用这个带空格的 key 去写请求头， 所以 PMUSER_CLIENT_IP 的取值永远为空。

迁移时顺手修成 x-authentic-ip（无空格）。 在 CloudFront 侧若保留同等语义，应在 CloudFront Function / Lambda@Edge 里显式使用无空格的 header name。

完整回源请求头行为：

  • 透传 True-Client-IP
  • ⚠ 注意 PMUSER_CLIENT_IP 的 Parent 层 extract 指定从请求头 " x-authentic-ip"（前导空格）提取 —— HTTP 规范不允许 header name 有前导空白，几乎必然是 bug，取值永远为空。迁移时顺手修成 x-authentic-ip。
  • modifyOutgoingRequestHeader 自定义头（值见 raw JSON）

§11 动静态判定

最终结论——纯动态。详细动静态分析见 模块 90。

API-DOM-11结论：纯动态
纯动态
类型：纯动态。详见 90-dynamic-static.html。
  • 默认 NO_STORE + Sureroute&Caching 双重 NO_STORE → 所有 API 请求默认回源
  • 缓存仅在源站 Cache-Control: public, max-age=… 明确允许时才生效
  • 即便可缓存，也按 customer_group、currency cookie 拆版本 → 缓存命中率天然受限
  • 广告追踪参数已剔除出 cache key → 拆版本污染被最小化
